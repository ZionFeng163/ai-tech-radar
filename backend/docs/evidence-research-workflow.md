# 证据研究工作流

深度分析不再假设采集到的摘要已经足够，也不针对某个站点或某种文章单独修补。系统先把
来源统一转换为可核对的证据文档，再允许模型分析：

```text
Article
  → 候选资料发现
  → URL 策略与安全校验
  → 下载
  → 按媒体类型解析
  → 证据覆盖判断
  → 编号证据片段
  → 深度分析
  → 逐字引用校验
  → AnalysisRun 审计
```

## 当前边界

- `EvidenceCandidate` 描述候选地址、来源和优先级。
- `EvidenceResolver` 是获取工具协议；工作流不依赖某个站点。
- `ContentExtractor` 按媒体类型注册，当前支持 PDF、HTML、JSON 和纯文本。
- URL 变换属于解析层。例如 GitHub `blob` 链接转换为原始文件地址，不会污染分析流程。
- HTTP 获取只允许公网 HTTPS；每次重定向都会重新执行地址校验，防止跳入内网。
- 单文档限制 30 MB，每篇最多尝试 3 个外部文档，并与模型输入共享字符预算。
- PDF 不只读取第一页：优先保留开头，同时抽取中段实验和末尾结论的代表页。
- 不同来源正文都会转换为不超过 800 字符的稳定编号片段。模型可以借助编号定位，但
  `evidence_quote` 只能连续复制单个片段的正文，不能携带编号、使用省略号或跨片段拼接。
- 引用匹配忽略 HTML/PDF 解析可能造成的空白差异，但不忽略文字差异；这兼顾了解析容错和
  事实边界。
- 每次请求记录尝试地址、解析器、内容哈希、提取字符数、覆盖级别和分阶段失败原因。
- 模型输出中的 `verified_facts` 必须逐字命中原始或外部证据，分析推断不能冒充来源事实。
- 结构校验失败时，下一轮会附带上次输出，要求保留其他字段并只修复不合格引用，避免整份
  分析重写后重复同一种错误。

## 失败语义

获取失败被归到 `policy`、`resolve`、`redirect`、`download` 或 `extract` 阶段。单个候选失败
不会让整个研究流程失去诊断信息；工作流会尝试下一个候选。证据仍然过薄时，模型只能输出
边界明确的分析，不能用常识补齐。

## 为什么暂不引入 Agent 框架

当前瓶颈是可靠的获取、解析和引用验证，而不是模型不会规划。LangGraph、PydanticAI 等框架
可以编排工具，却不会自动解决 PDF 解析、网页噪音和证据质量。先稳定工具协议和状态模型，
以后出现以下需求时再在工作流外增加 Agent/持久化编排层：

1. 需要从页面继续发现论文、仓库、官方公告等二级资料；
2. 需要根据证据缺口多轮选择搜索工具；
3. 任务跨进程恢复、人工确认或长时间运行；
4. 需要持久化文档缓存，并按内容哈希复用证据。

那时 Agent 只负责选择候选和决定是否继续，下载预算、安全策略、证据校验仍由当前确定性
工作流强制执行。

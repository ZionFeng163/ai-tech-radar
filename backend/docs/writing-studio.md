# 写作工作台

写作工作台把单篇热点转换为可人工控制的短帖、Thread 或 X 长文。写作链路固定为“抓取 → 深度分析 → 写作角度 → 草稿 → 审校”，快速概览只用于首页筛选，不能直接生成角度或正文：

1. 深度分析先整理已核实事实、技术机制、证据缺口、反对意见、二阶影响、开放问题和可写观点。
2. 基于热点原文和深度分析提出一到三个写作角度；只有标题和热度时只生成一个有依据的角度。
3. 作者选择角度；如果有特别想强调的内容，可以补充一句，也可以直接跳过。
4. 百炼 `qwen3.7-flash-2026-07-15` 按目标格式生成可编辑草稿。
5. 独立审校调用检查事实归属、论证、模板化 AI 腔和发布格式。

写作与资讯分析使用独立配置 `config/writing.json`。角度和审校使用 JSON Schema，正文使用纯文本；所有来源内容都被明确标记为不可信资料，不能覆盖系统提示。短观点推文目标约 180–300 字，最多 360 字符和 5 个段落；仅有标题与热度数据时控制在 110–220 字，最多 280 字符和 3 个段落。薄资料的深度分析推断只能作为观点线索，不能冒充来源事实，并且不开放长文生成。短 Thread 包含 3–4 条，每条 90–280 字符，总长度 420–850 字符，并要求每条增加新的事实、解释或判断，不能把短推文机械切段。后端还会检查一组已知报告式套话，生成不合格时最多进行定向压缩或改写。

正文的发布格式校验与编辑审校分开处理：字符数、Thread 条数等硬格式不合格时才要求模型
重写；格式合格后立即保留草稿，再执行一次事实、术语和 AI 腔审校。审校发现高风险问题时，
草稿和审校意见会同时返回，由用户修改或重新生成，不再以错误响应丢弃已经生成的正文。

默认受众是对 AI 和计算机感兴趣、但不熟悉当前项目的普通读者。短推文最多展开两个核心技术概念，第一次出现时要用白话说明作用；后端会限制英文术语和缩写堆叠。审校同时评价技术清晰度与公众可读性，不以删除全部技术内容换取通俗。

正文生成后会自动执行一次独立审校。公众可读性或技术清晰度低于 7 分，或者存在高严重度的事实、逻辑、术语问题时，草稿不会直接展示，而是携带具体审校意见自动重写。人工编辑后仍可使用“检查事实与 AI 腔”再次审校。

写作规则已整理为项目内的 `config/skills/tech-social-writer/`，百炼 API 会按阶段加载，而不是只供 Codex 使用：

- `SKILL.md`：证据边界、写作决策、格式预算和分阶段工作流。
- `references/voice-profile.md`：从作者认可与否定的样例中提炼出的声音档案。
- `references/fact-check.md`：只在草稿生成后的独立审校调用中加载。
- `references/chinese-edit.md`：生成和审校阶段使用的中文最小修补规则，明确禁止新增事实或虚构第一人称经历。

角度阶段只加载主 Skill 与声音档案；正文阶段再加入中文成稿规则；审校阶段才额外加载逐条事实核验。这样保持生成与核验分离，也避免每次调用携带所有参考资料。Skill 的事实核验方法参考了 MIT 许可的 [jwynia/agent-skills fact-check](https://github.com/jwynia/agent-skills/tree/main/skills/general/research/verification/fact-check)，声音建模参考其 `voice-analysis`；AI 文风检查参考 MIT 许可的 [avoid-ai-writing](https://github.com/conorbronsdon/avoid-ai-writing)，所有规则均针对本项目重新编写。

系统会在写作资料包中显式加入 `writing_style_profile`，避免所有内容共用一种机械结构：

- `technical_reading_notes`：有可靠原文的论文、模型、技术报告与仓库，采用“中心发现 → 数字对照 → 组件作用 → 设计归纳或实验结果”的技术笔记结构。
- `technical_findings`：技术资料不完整时仍解释具体发现，但不得伪造“读完报告”的第一人称经历。
- `editorial_commentary`：融资、政策、人物观点和社区热点按事件与判断展开，不硬套技术报告拆解。

技术写作优先回答“和上一代或基线相比具体改了什么、每个组件负责什么、数字是否支撑中心判断”。短帖只保留最有说服力的一组对照，Thread 再逐步展开组件和结果；不把参数表照抄成正文，也不从技术细节强行跳到宏大趋势。

## 数据边界

每篇文章最多关联一个 `WritingProject`。第一阶段只保存当前角度、作者输入、当前草稿和当前审校结果：

- 重新生成角度会清空旧草稿和审校。
- 重新生成正文会覆盖旧正文和审校。
- 人工保存正文会覆盖当前正文并清空过时审校。
- 删除孤立文章时，写作项目通过外键级联删除。

这样不会因反复生成建立无限版本历史。后续如果增加版本历史，必须同时增加数量或时间保留策略。

## API

- `POST /articles/{article_id}/writing-project`：获取或创建工作台。
- `GET /writing-projects/{project_id}`：读取当前状态。
- `POST /writing-projects/{project_id}/angles`：生成三个角度。
- `POST /writing-projects/{project_id}/draft`：按选定角度和作者输入生成正文。
- `PATCH /writing-projects/{project_id}`：保存人工修改。
- `POST /writing-projects/{project_id}/review`：审校当前正文。

模型密钥继续通过 `DASHSCOPE_API_KEY` 注入，数据库需升级到 Alembic `0009_writing_projects`。

## 后续阶段

- 第二阶段：多热点合并为同一事件、逐条 claim 与来源映射、可复用声音档案。
- 第三阶段：保存有限版本、记录模型原稿到最终稿的修改差异、从人工选择中学习偏好。
- 第四阶段：长文与 Thread 双向改写、发布前检查清单和效果反馈；不自动发布。
